# Руководство для разработчиков

Документ описывает устройство репозитория, запуск и проверку приложения, замер распознавания планов этажей, правила оформления коммитов и порядок работы с моделями ИИ.

## 1. Обязательные правила проекта (из AGENTS.md)

1. **Работа без сети**: приложение не делает ни одного обращения в интернет. Все библиотеки и шрифты лежат в `vendor/`. Каждый новый файл приложения обязательно добавляется в массив `ASSETS` в `sw.js`.
2. **Расчётный модуль и нормы**: изменения в расчёте (`js/engine.js`, `js/plan.js`) вносятся только вместе с тестами. Таблицы в `js/norms.js` сверены с официальным текстом Правил пожарной безопасности РК по каждой ячейке, вручную их не править.
3. **Проверки перед сдачей**: `npm test`, `npm run check:ui`, `node tools/check-pwa.js`; после изменения файлов приложения запускается `npm run build` (обновляет номер сборки). При правках распознавания планов дополнительно запускаются `node tools/bench-vision.js` и `node tools/vision-gallery.js`.
4. **Совместимость и зависимости**: существующий код в `js/` работает без сборщика и без внешних зависимостей времени выполнения. Операторы `?.` и `??` в файлах старого приложения не используются, чтобы код работал в старых Android WebView.
5. **Язык кода**: комментарии, названия тестов и сообщения коммитов пишутся на русском языке, коротко и по делу. В новых комментариях, строках и сообщениях коммитов не используются длинное тире и средняя точка.
6. **Тексты и оформление**: тексты интерфейса и документов оформляются по [docs/style.md](docs/style.md), внешний вид по [docs/design.md](docs/design.md). PDF-отчёт остаётся строгим служебным документом (шрифт Tinos, чёрный текст, цвет только в знаках безопасности).
7. **Защита служебных данных**: реальные планы объектов проверки, персональные данные и ключи подписи никогда не отправляются во внешние сервисы, включая модели ИИ. Для отладки и замеров используются синтетические планы и общедоступные планы из `bench/vision/`.
8. **Ключ подписи APK**: папку `%LOCALAPPDATA%\firecalc-build\keys` не изменять и не копировать в репозиторий.

## 2. Требования к окружению

- **Node.js 22** (используются встроенные `node:test`, `fetch`, `WebSocket`).
- **Microsoft Edge или Google Chrome** для безголовых проверок интерфейса (`tools/check-ui.js`) и работы без сети (`tools/check-pwa.js`) через протокол DevTools (`tools/cdp.js`). Если браузер установлен в нестандартную папку, укажите путь в переменной окружения `BROWSER`.
- Для сборки Android APK (`node tools/native.js android`): **JDK 21** и **Android SDK** (платформа `android-36`, `build-tools` 35+). Пути берутся из `JAVA_HOME` и `ANDROID_HOME` либо из папки `%LOCALAPPDATA%\firecalc-build` (`jdk`, `android-sdk`).
- Для сборки Windows EXE (`node tools/native.js windows`): Windows 10 или 11 (64-бит). Зависимости Capacitor и Electron устанавливаются автоматически в рабочую копию `%LOCALAPPDATA%\firecalc-build\work\native` из `native/package.json`.

## 3. Запуск при разработке

Корневое приложение не требует сборки для запуска в браузере. Достаточно раздать корень репозитория любым локальным HTTP-сервером:

```
python -m http.server 8765
```

Или запустить встроенный сервер из `tools/cdp.js`:

```
node -e "require('./tools/cdp.js').serve(8765); console.log('http://127.0.0.1:8765/')"
```

Полезные адреса для проверки в браузере:
- `http://127.0.0.1:8765/index.html?demo=business`: пример «бизнес-центр» с тремя огнетушителями на схеме первого этажа (включая порошковый в серверной), выходом и пожарным краном;
- `http://127.0.0.1:8765/index.html?demo=factory&open=all`: пример «производственная база» с раскрытыми расчётами по помещениям;
- `http://127.0.0.1:8765/index.html?selfcheck=1&demo=business`: самопроверка формирования PDF в браузере;
- `http://127.0.0.1:8765/tests/ui-smoke.html`: прогон проверок интерфейса прямо во вкладке браузера.

Когда в репозитории присутствует папка `app/` (приложение версии 2.0 на Vite, Vue 3, TypeScript и Ionic):
- `npm run app:dev`: сервер разработки приложения 2.0;
- `npm run app:build`: сборка приложения 2.0;
- `npm run app:preview`: предпросмотр собранного приложения 2.0.

## 4. Тесты и проверки

Все проверки запускаются из корня репозитория:

```
npm test                   # модульные тесты (node --test)
npm run check:ui           # проверка интерфейса в браузере без окна (tests/ui-smoke.html)
node tools/check-pwa.js    # проверка манифеста, кэша sw.js, работы без сети и обновления
node tools/build.js --check # проверка соответствия номера сборки содержимому файлов
```

Что проверяют модульные тесты в `tests/`:
- `tests/engine.test.js`: таблицы норм, расчёт по категориям и классам пожара, правила п. 5, 6, 7, 9, 10 Приложения 3, передвижные огнетушители, 3000 случайных объектов;
- `tests/golden.test.js`: эталонные объекты и примеры;
- `tests/plan.test.js`: геометрия схемы этажа, расстояния до огнетушителей, авторасстановка по нормам, перечень нарушений;
- `tests/signs.test.js`: знаки безопасности по ГОСТ 12.4.026-2015 (ISO 7010);
- `tests/vision.test.js`: распознавание помещений, масштаб по отрезку и по площади, поглощение мебели, большие здания;
- `tests/vision-geom.test.js`: поиск четырёхугольника плана на снимке, выпрямление перспективы, обрезка области здания;
- `tests/synth.test.js`: генератор синтетических планов и метрики сопоставления контуров;
- `tests/report.test.js`: структура PDF-отчёта, отсутствие запрещённых знаков и цветных плашек;
- `tests/pwa.test.js`: список `ASSETS` в `sw.js`, манифест, совпадение номера сборки в `sw.js`, `index.html` и `js/config.js`.

Дополнительные проверки приложения 2.0 (когда есть `app/index.html`):

```
npm run lint               # ESLint
npm run typecheck          # tsc --noEmit
npm run test:unit          # Vitest (хранилище, обёртка расчёта, переводы, компоненты)
npm run test:e2e           # Playwright (телефон и компьютер, без обращения во внешнюю сеть)
```

После любого изменения файлов из списка `ASSETS` в `sw.js` обновите штамп сборки:

```
npm run build
```

## 5. Замер распознавания планов этажей

Для объективной оценки изменений в `js/vision.js` и `js/vision-geom.js` используется стенд распознавания:

```
node tools/bench-vision.js --synth          # только синтетические планы (16 вариантов x 3 сида)
node tools/bench-vision.js --real           # только реальные планы из bench/vision/img/ (59 планов)
node tools/bench-vision.js                  # полный прогон (синтетика + реальные планы)
node tools/bench-vision.js --only hollow    # один вариант синтетики, вид или идентификатор плана
node tools/bench-vision.js --by-area        # синтетика в двухпроходном режиме по площади этажа
node tools/ci/bench-gate.js --max-drop 2    # проверка порога: падение не более 2 пунктов к baseline.json
node tools/vision-gallery.js                # страница bench/vision/out/index.html с контурами по 59 планам
```

Как устроен стенд:
- **Синтетические планы** (`tools/synth-plans.js`): создаются на лету с точным эталоном контуров и площадей (`clean`, `hollow`, `door-arcs`, `windows`, `furniture`, `toilets`, `open-plan`, `stubs`, `gray-walls`, `colored-walls`, `evacuation`, `sheet`, `photo`, `lowres`, `tight`, `two-buildings`). Считаются точность (precision), полнота (recall), F1 (micro и macro), число разрезанных (`splits`) и слитых (`merged`) помещений, медиана и 90-й перцентиль ошибки площади, доля опасных занижений площади более чем на 10 % (`under10Share`).
- **Общедоступные планы** (`bench/vision/`): 59 планов со свободной лицензией из Wikimedia Commons. Источники и лицензии перечислены в `bench/vision/sources.json`, ожидаемое число помещений и рамка здания в `bench/vision/expect.json`. Сами изображения лежат в `bench/vision/img/*.png`, а отчёты и галерея записываются в `bench/vision/out/`. Папки `bench/vision/img/` и `bench/vision/out/` в git не добавляются.
- **Базовый замер** (`bench/vision/baseline.json`): хранится в git. В CI (`ci.yml`) на каждом коммите запускается `node tools/bench-vision.js --synth` и `node tools/ci/bench-gate.js --max-drop 2`: если балл падает более чем на 2 пункта ниже базового замера, проверка завершается с ошибкой. Обновлять `baseline.json` флагом `--save-baseline` допускается только по согласованию при принятии этапа плана.

## 6. Стиль коммитов и пулреквестов

- Сообщения коммитов пишутся на русском языке в одну короткую фразу без точки в конце: что именно сделано (например, `Поиск углов плана, обрезка здания и перспективное выпрямление`).
- Не используйте длинное тире и среднюю точку в сообщениях коммитов, комментариях и строках.
- Изменения группируются в логические коммиты. Не смешивайте рефакторинг интерфейса, правки расчёта и обновление документации в одном коммите.
- При оформлении пулреквеста заполняйте шаблон `.github/pull_request_template.md`: что изменено, какие проверки прогнаны, числа стенда до и после (для правок распознавания), снимки экрана (для правок вида), возможные риски.

## 7. Порядок работы с моделями ИИ

Разработка ведётся с участием моделей ИИ по правилам раздела Г [docs/plan.md](docs/plan.md) и [docs/adr/0007-model-workflow.md](docs/adr/0007-model-workflow.md):

1. **Постановка задания**: каждое задание оформляется отдельным файлом в `docs/briefs/<имя>.md`. Общие правила для всех заданий лежат в `docs/briefs/common.md`. В задании явно перечисляются ветка, файлы, которые разрешено менять, требования и команды проверки.
2. **Изолированная рабочая копия**: каждая модель работает в отдельном дереве git (`git worktree` в `%LOCALAPPDATA%\firecalc-build\wt\<ветка>`) на своей ветке, чтобы параллельные задания не мешали друг другу.
3. **Запрет на `npm run build` в ветках заданий**: модели в рабочих ветках не запускают `node tools/build.js` и `npm run build`, чтобы не создавать конфликты слияния в `index.html`, `sw.js` и `js/config.js`. Игнорируется только падение проверки штампа сборки в `tests/pwa.test.js`; все остальные тесты обязаны проходить. Штамп сборки обновляется после слияния в `main`.
4. **Перекрёстная проверка и приёмка**: выполненную ветку сначала проверяет другая модель в режиме только для чтения по шаблону `docs/briefs/review.md` (сверка с заданием по пунктам, запуск тестов и стенда, проверка качества кода и соблюдения правил проекта). После этого координатор проверяет `git diff`, прогоняет тесты и стенд, сверяет снимки экранов и сливает ветку в `main`.
