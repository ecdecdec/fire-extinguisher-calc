# ADR 0007: Порядок распределения работ и перекрёстной проверки между моделями ИИ

## Статус

Принято (24.11.2026).

## Контекст

Разработка версии 2.0 включает параллельные задачи разного характера: математически насыщенные алгоритмы компьютерного зрения (`js/vision.js`, `js/vision-geom.js`), перенос интерфейса на стек Vite + Vue 3 + TypeScript + Ionic (`app/`), настройку безопасности оболочек Electron и Capacitor (`native/`), подготовку нормативных отчётов и документации.

Если одна модель одновременно правит много файлов в одной рабочей папке или её код сливается без независимой проверки:
- возникают конфликты правок и перезапись чужих изменений;
- остаются незамеченными краевые ошибки, отступления от требований задания или нарушения ограничений проекта (например, использование `?.` в старом коде, длинных тире, обращений к сети или изменение штампа сборки);
- при исчерпании квоты одной модели работа останавливается.

Кроме того, проект работает со служебной предметной областью ДЧС, поэтому реальные планы объектов, персональные данные и ключи подписи не должны попадать во внешние ИИ-сервисы.

## Решение

1. **Распределение ролей**:
   - **Координатор (Claude)**: ведёт план работ ([docs/plan.md](../plan.md)), составляет точные технические задания в `docs/briefs/`, создаёт изолированные рабочие ветки, принимает проверенные результаты, выполняет слияние веток, запускает `npm run build` и собирает установочные пакеты.
   - **Исполнители (модели Gemini 4 через `agy`)**:
     - `Neon XHigh`: сложные алгоритмические задачи (стенд распознавания, геометрия и выпрямление плана, свет и цвет, строение стен, сегментация помещений, каркас нового приложения 2.0);
     - `Argon High` и `Neon High`: перенос компонентов, доводка оболочки Windows и безопасности, документация, исправления по замечаниям и перекрёстная проверка.
   - **Резерв при исчерпании лимитов**: если квота `agy` (Gemini) исчерпана, работу по тем же заданиям из `docs/briefs/` в тех же рабочих копиях (`git worktree`) продолжают отдельные агенты Claude Sonnet либо новая сессия Gemini с явной пометкой о продолжении и критической проверкой незавершённого коммита.
2. **Изоляция через `git worktree` и строгие границы задания**:
   - под каждое задание создаётся отдельная рабочая копия репозитория в `%LOCALAPPDATA%\firecalc-build\wt\<ветка>` на собственной ветке;
   - в каждом файле `docs/briefs/<задание>.md` и в `docs/briefs/common.md` жестко задан список файлов, которые разрешено изменять;
   - модели в рабочих ветках не запускают `npm run build` (`node tools/build.js`), чтобы не менять штампы в `index.html`, `sw.js` и `js/config.js` до слияния.
3. **Двухступенчатая приёмка (перекрёстная проверка моделью и приёмка координатором)**:
   - после завершения задания ветку проверяет другая модель (например, `Argon High` проверяет работу `Neon XHigh`) в режиме только для чтения (`--sandbox`) по шаблону `docs/briefs/review.md`: сверяет каждый пункт задания, запускает тесты и стенд, проверяет соблюдение `AGENTS.md`, `docs/style.md` и `docs/design.md`, оценивает риски слияния и выносит вердикт (`MERGE`, `MERGE AFTER FIXES` или `REJECT`);
   - затем координатор (Claude) просматривает `git diff`, отчёт проверяющей модели, результаты тестов, цифры стенда и снимки экранов, при необходимости назначает задание на исправление замечаний и только после этого сливает ветку в `main`.
4. **Защита данных при работе с моделями**:
   - в модели ИИ передаются только исходный код, синтетические планы и общедоступные планы со свободной лицензией из `bench/vision/`;
   - реальные планы объектов ДЧС, персональные данные и папка ключей подписи (`%LOCALAPPDATA%\firecalc-build\keys`) во внешние сервисы не отправляются.

## Последствия

- Несколько крупных задач выполняются параллельно без конфликтов в файловой системе и без поломок основной ветки `main`.
- Каждое задание оставляет прозрачный след в репозитории: текст поручения в `docs/briefs/`, коммиты в ветке и результаты автоматических проверок.
- Перекрёстная проверка другой моделью до слияния отлавливает алгоритмические и стилевые ошибки без ручной построчной отладки координатором.
- При остановке агента по лимиту работа продолжается без потери контекста с последнего зафиксированного состояния ветки.
